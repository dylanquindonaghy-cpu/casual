### M4. Error pages' 'Try again' calls reset(), which does not re-fetch in Next 16.3, so it can't recover from a server-side failure

- **Where:** `src/app/error-body.tsx:46` (audit slice: p3)
- **Owner:** Phase 10 task 14

Task 10 added src/app/error.tsx and global-error.tsx with a 'Try again' button wired to the boundary's reset(). In the installed Next 16.3.6, reset() only does setState({error:null}) and re-renders the children from the RSC payload already on the client. retry() is the prop that calls router refresh and then reset. When a server component fails (a database timeout on My shifts, say), the cached payload still holds the error, so the page throws again and the error screen stays. On `/` the second button, 'Go to my shifts' (href='/'), does not change the pathname either. The boundary only clears its error on a pathname change, so neither button recovers on the portal's main page, and the worker needs a manual browser reload. This breaks rule 11 ('buttons say what happens') on the exact screen the task delivered. The case it fails in is the product's core one: a flaky connection at a venue. The copy test renders ErrorBody with a no-op reset, and no browser test clicks Try again, so nothing catches it. CLAUDE.md tells builders to read node_modules/next/dist/docs before writing Next code. Those docs say to use retry().

**Evidence:** src/app/error-body.tsx:44-50 `onClick={reset}`; src/app/error.tsx:26 `({ reset })`; src/app/global-error.tsx:7,17. node_modules/next/dist/client/components/error-boundary.js:39-47 (reset = setState only; retry = startTransition(refresh(); reset())), :81-89 (clears only when pathname changes). node_modules/next/dist/docs/01-app/03-api-reference/03-file-conventions/error.md:117-121,155-157.

### M13. Unauthenticated CPU exhaustion: log masker's regexes are quadratic and run on every request path

- **Where:** `src/lib/log/mask.ts:25` (audit slice: g-security)
- **Owner:** Phase 10 task 16

The proxy logs every request's pathname through the masking logger. It does this for every host, before the unknown-host 404 and before any auth. maskText() then runs the EMAIL regex and the URL_TAIL regex over the whole string. Both backtrack quadratically on long runs: letters, digits and dots with no '@' for EMAIL, and many '/' with no '?' or '#' for URL_TAIL. The proxy runs in the Node.js runtime inside the single web process (Next 16 proxy.md:255), so this work blocks the event loop. I timed it with the real createLogger (pure CPU, no server): an 8k-character path took 86 ms and a 16k-character path about 295 ms. Node's 16 KB header limit allows paths of about 16k characters. So a few crafted requests per second from one client, at about 16 KB each, keep the one web process busy. That stalls logins, pages and the Twilio webhooks for every firm at once. The Docker healthcheck marks the container unhealthy, but restart: unless-stopped does not restart it. The existing performance test covers only the PHONE regex (tests/unit/log.masking.test.ts:202-206). EMAIL and URL_TAIL are untested. Fix options: truncate strings before masking (a path cap of about 512 characters is plenty); only run EMAIL when the text contains '@' and URL_TAIL when it contains '?' or '#'; or rewrite both without unbounded overlapping quantifiers. Add a timing test for both.

**Evidence:** src/lib/http/proxy.ts:27-32 `logger.info("request", {... path: request.nextUrl.pathname })` runs before `if (!match && !internal)` at :35. src/lib/log/mask.ts:25 `const EMAIL = /[A-Za-z0-9._%+-]+@(...)/g`, :32 `const URL_TAIL = /((?:https?:\/\/[^\s"'<>?#]+)|(?:\/[\w.~%/-]*))[?#][^\s"'<>]*/gi`, applied at :55-56. src/lib/log/index.ts:31 redacts every field. Measured: `"/"+"a".repeat(16000)` took 295 ms; `"/a".repeat(8000)` took 199 ms.

### M17. Google Sheets dates are read as text in the sheet's locale but always parsed as dd/mm; a US-locale sheet silently swaps day and month

- **Where:** `src/lib/roster/sheets/google.ts:146` (audit slice: gap1-import-parsing)
- **Owner:** Phase 10 task 10

The Sheets client asks for FORMATTED_VALUE, so dates arrive as the sheet displays them. parseSheetDate always reads d/m/yyyy (parse.ts:120-121).
