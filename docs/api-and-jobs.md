# API, webhooks and jobs

## Principles

- Public HTTP surface is tiny: webhooks, push subscription, Caddy's domain check, health, and the
  planner API (`/api/v1`, 12J.1). Everything else is Next.js server actions behind sessions.
- Webhooks: verify signature → insert message (idempotent) → enqueue job → return 200 within
  a second. Never do AI or Sheets work inside a webhook.
- The planner API is not a provider webhook (golden rule 3; ADR-022): each write is one short
  transaction answered in the request, made idempotent by the planner's own ref. Offer waves,
  notices and travel estimates still go to jobs.
- Every job payload includes `firm_id` and an idempotency key. Jobs are safe to retry.

### Twilio webhooks: checks and storing once (Phase 7)

Every Twilio webhook hands the request to one handler in `src/lib/inbound/` whose first step is
`readTwilioRequest()` (`src/lib/inbound/twilio-request.ts`), and a refusal returns at once:

1. no `TWILIO_AUTH_TOKEN` configured: 503 (Twilio isn't connected);
2. not a form post: 415; bigger than 64 KB (by its declared length before reading, then by what
   arrived): 413;
3. a field sent twice (Twilio never does): 400;
4. `X-Twilio-Signature` missing or wrong: 403. It's checked against the webhook's own address as
   configured (`platformUrl(APP_BASE_DOMAIN, path)`), never the address the request claims, so a
   request signed for one webhook isn't valid at another. HMAC-SHA1 of the address and the sorted
   fields, compared in constant time (`src/lib/inbound/twilio-signature.ts`, which reproduces
   Twilio's published example).

Only then are the fields checked (zod: 400) and the firm found by the number (none: 200, nothing
stored, so Twilio doesn't retry). Nothing from a request is logged.

| Webhook | Stored once by | A repeat (Twilio's retry, or a replayed request) |
|---|---|---|
| `whatsapp` | MessageSid | stores nothing, queues nothing |
| `sms` | MessageSid | stores nothing, queues nothing |
| `voice` | CallSid (a withheld number's too) | the same answer; no second row, event or login link |
| `voice/transcription` | RecordingSid | stores nothing, queues nothing |
| `voice/done` | nothing (it only says goodbye) | the same goodbye |

Twilio's signature has no timestamp, so a captured request stays valid: storing each Twilio id at
most once is the defence. The key is unique within the firm (`messages (firm_id,
provider_message_id)`); the insert is `ON CONFLICT DO NOTHING`, and the job (or event, or login
link) follows only when a row came back. Two copies at the same moment: `ON CONFLICT DO NOTHING`
waits for the other's insert, then inserts nothing. `tests/unit/twilio.webhooks.test.ts` holds every webhook, now
and future, to this shape; each webhook's integration tests prove it (refusals store nothing, a
repeat stores and sends nothing more), with `tests/integration/webhook.idempotent.test.ts` (ten
copies at once) and `tests/integration/twilio.contract.test.ts` (Twilio-shaped requests signed as
Twilio signs them).

### The planner API (12J.1)

The firm's planner or CRM sends its sessions and reads bookings and cancellations
(`docs/office-v2.md` §5.3.2; ADR-022). The planner's own guide, with every field, error code and
limit and a curl example of each call, is `docs/integrations.md`.

Every call goes through `handleApiRequest()` (`src/lib/integrations/api.ts`), and a refusal answers
at once, in this order:

1. **The platform address only** (`parseHost()` gives "apex" for `APP_BASE_DOMAIN`): a firm's
   subdomain or its own domain gets 404 `not_found`. The proxy never redirects an `/api/` path for
   trailing punctuation (`src/lib/http/proxy.ts`), so a ref ending in "." gets the API's own 400
   `bad_ref`, never a 308 that carries the key on to another address.
2. **`INTEGRATIONS_SECRET` unset:** 503 `not_configured`.
3. **Refused keys, counted per client address** in the web process's memory
   (`src/lib/integrations/refused-keys.ts`: `X-Real-IP` as `clientIpFrom()` reads it, a /64 for
   IPv6; one fixed minute; at most 10,000 addresses a minute): after 30 refusals in a minute, 429
   `rate_limited` with `Retry-After` until the minute ends, before any look-up. `throttle()` can't
   count these: it needs a firm.
4. **The key's shape** (`Authorization: Bearer shiftdesk_…`, `looksLikeApiKey()`): anything else is
   401 `invalid_key` without touching the database, and counted (3).
5. **The look-up**, `resolveApiKey()` (`app_api_key_lookup()`, an owner-run function: the firm and
   key id of a live key, by the key's sha256): none is the same 401 for a wrong key and a revoked
   one, and counted (3). From here on the key's firm is the only one: every query runs in
   `withFirm(firmId)`.
6. **300 calls a minute per key**, through `throttle()` (`LIMITS.apiPerKey`, bucket `api:key`, the
   key's id): 429 with `Retry-After` in seconds; `auth.rate_limited {limit: "api:key"}` logged once
   a window.
7. **`last_used_at`**, at most once a minute (a memo per process, and the update's own condition),
   in a short transaction of its own that skips a locked row rather than wait for it: a change
   under way holds the key's row (`src/lib/roster/firm-caller.ts`).
8. **A body** (PUT): `application/json` (else 415 `not_json`), at most 64 KB by its declared length
   before reading, then by what arrived (else 413 `too_big`), strict UTF-8 JSON (else 400
   `bad_json`). Every body is a `z.strictObject` (`src/lib/integrations/schemas.ts`): an unknown
   field is 400 `validation_failed`, with `fields: [{path, code}]` and never a value.
9. **The call's handler.**

Each request writes one log line ("api request": request id, route pattern, method, status,
milliseconds, firm id, `keyId`; an error line for a 500): never the key, the `Authorization`
header, a body or the path. Every error body is `{"error": {"code", "message", "request_id"}}`
with fixed words (`src/lib/integrations/errors.ts`); a value sent in is never echoed back. No
cookie is read and no CORS header is sent.

**A PUT** (`putSession()`) checks the ref and the body first. A site postcode is looked up first,
outside any transaction, only when the site has none (`serverGeocoder()`; an unknown postcode is
422 `unknown_postcode`, a failed look-up 503 `lookup_failed`, look-ups off save it without a point),
and a site that already has a different postcode is 409 `site_postcode_differs`. Then one
transaction (a deadlock retries it): Gate B (`requireAgreementForImport()`: 403
`agreement_not_recorded` on a live database without the firm's recorded agreement); the key still
live, its row held `for share` before the session's (`firmCallerMay()`); the session locked by
`(source "api", external_ref)`.
- **A new ref:** role, times and site required; a start in the past is 409 `session_started`;
  `"status": "cancelled"` creates nothing (200 `unchanged`); the role must be one of the firm's
  role codes (`credential_rules.role`, else 422 `unknown_role`) and the requirements its
  qualification codes (`credential_types`, else 422 `unknown_requirement`). The site is found or
  made by name and the event by `(source "api", planner_ref)`, each with `insert … on conflict do
  nothing` and read back (two PUTs naming one new site or event share one row); without an event,
  the site and day's automatic event. A new site is `site.created`, a filled postcode
  `site.changed {siteId, fields: ["postcode"]}` with `siteMoved()` (its sessions' travel
  estimates). The session: `source "api"`, open, `shift.created`, travel estimates queued. Two PUTs
  for one new ref: the second's insert waits on the unique key and then updates the first's.
- **Nothing different:** 200 `unchanged`, nothing logged. **Cancelled or started:** 409
  `session_cancelled` / `session_started`.
- **`"status": "cancelled"`:** decided first, nothing else applied (the site step before the
  transaction is skipped too); the same cancellation again is 200 `unchanged`; a `change_reason`
  (else 422 `change_reason_required`, logged `api.change_refused` when casuals are booked), then
  `cancelShiftInTx()` with the API caller.
- **Nobody booked:** applied, `shift.changed {fields, from/to when the times or site changed}`;
  offers still out expire and travel estimates are queued when the times, site or role changed.
- **People booked:** role or requirements: 409 `session_has_bookings`; places below the highest
  booked place: 409 `places_below_booked` (each also logged `api.change_refused {shiftId, code}` in
  a transaction of its own after the rollback, for the office's Needs attention); new times or
  site: a `change_reason` (else 422 `change_reason_required`, also logged `api.change_refused` for
  Needs attention), then `moveShiftInTx()` with the API caller, where any failed rules check
  throws `MoveBlocked`, everything rolls back, `shift.move_refused` is logged with `via: "api"`
  (`recordMoveRefused()`) and the answer is 409 `bookings_block_change` with each casual's id and
  codes; the rest (places, pay, post, meeting point, uniform, instructions, event) is applied and
  logged.
- The status follows the places (`refreshShiftStatus()`, `shift.reopened` when it opens again),
  unless the office closed the session (filled with places free).

Every entry is logged with the system actor and `{by: "firm", via: "api", keyId}`. Field names in
`shift.changed`: `role`, `startsAt`, `endsAt`, `siteId`, `headcount`, `payRatePence` (a casual's
later cancellation is then exempt from a strike), `post`, `meetingPoint`, `uniform`,
`instructions`, `requirements`, `event`, `eventName`.

**Records** (`src/lib/integrations/records.ts`, shared with 12J.2's webhooks): the session (its
planner ref, event and its ref when the planner named it, site name and postcode, role, times,
status, places, booked, pay, post, meeting point, uniform, requirements) and the booking (id, its
office reference, status, the casual's id, staff ref and name or `null` with `erased: true`, when
and by whom it was booked, and for a cancellation when, by whom, how, notice hours, a reason code
and the strike result with the casual's live strikes). Never a mobile, email, a casual's postcode
or travel data, a typed reason, a review flag or a withdrawal reason.

## Offer-wave ranking

1. Eligible per rules engine (credentials, overlap, rest, hours cap, not blocked, available).
2. Exclude workers who declined this shift or were offered it in an earlier wave, and (12G.3; D2)
   casuals whose travel area rules the shift out: every way they chose has an estimate and none is
   within their limit (`outsideArea()`, `src/lib/travel/area.ts`). An unknown distance (no
   estimate yet, or a site with no location) is still offered; a casual with no area is offered
   everything. The office's "Offer to someone" isn't limited by it (`byHand`: the office may offer
   outside a casual's area).
3. Sort:
   - `fair_rotation`: fewest confirmed hours this week → longest since last offer → a shuffle fixed
     by the shift and wave (Phase 10 task 19: the same wave always ranks the same, but the lowest
     worker ids no longer always win ties).
   - `first_come_first_served`: the same order (P4.3; `PLAN.md` "Connecting the firm's systems"
     10). Until P4.3 everyone eligible got the offer at once: at a big firm, about 1,500 texts
     (about £300 at 20p) for one place. The board still shows the shift to everyone eligible, and
     the first tap wins.
   (`rankForFairRotation()` in `src/lib/rules/allocation.ts` is the order for both.)

**On the Open shifts board** (built, Phase 3): under `fair_rotation` a newly opened place (the
shift's creation, or its latest cancellation) is held for `wave_minutes` for the `wave_size`
eligible-role workers with the fewest confirmed hours in the shift's week (ties included), unless
the shift starts within `urgent_window_hours` (default 24: late dropouts fill at once), the window
would run past the start, the shift isn't open, or the worker is already on it; `bookShift()` answers a worker outside that group `not_yet`
with the time it opens to them and logs `shift.booking_held`
(`loadAllocationGate()` in `src/lib/roster/allocation-input.ts`, `allocationGate()` in
`src/lib/rules/allocation.ts`). Office bookings and the office's sheet are never held. Settings:
`allocation_mode` (default `first_come_first_served`), `wave_size` (4), `wave_minutes` (15); a value
that makes no sense stops the booking.
4. Wave size and minutes from firm settings (`waveCap()` in `src/lib/offers/waves.ts`): under
   fair rotation `wave_size` (default 4); under first come, first served `wave_per_place` (default
   5, 1 to 20) times the free places, at most 50, worked out again at every claim. `wave_minutes`
   (default 15) apart in both modes. Cap: max 3 offers per worker per day unless urgent
   (built: `mayOfferToday()` in `src/lib/rules/offer-cap.ts`, asked by `waveCandidates()` for every
   worker; "urgent" is the shift's own `is_urgent`, read by the candidate list, never passed in). "A
   day" is the firm's calendar day (midnight to midnight, in the firm's time zone). Every offer the
   worker got that day counts, urgent ones too; one that failed to send doesn't. The 3 is fixed
   policy, not a firm setting.
5. Quiet hours: hold non-urgent offers until the window opens; urgent may override if the firm
   allows it.

## Firm-initiated changes (compliance-critical)

When the office (or, from 12J.1, the firm's planner through the API: `src/lib/roster/firm-caller.ts`)
cancels, moves or shortens a shift with workers assigned:
1. Require a reason.
2. For each assigned worker: write an event with `notice_hours` and the change type
   (`cancelled_firm`, `moved`, `curtailed`), old and new times.
3. Notify each worker (template `shift_changed_by_firm`).
4. These rows feed the notice report; short-notice flag uses the firm threshold.

Built in Phase 5, on the office's shift page ("Move, shorten or cancel"; each booking's "Cancel
{name}'s booking"):
- **Reasons** are a fixed list (`src/lib/roster/firm-reasons.ts`): "The event's times or place
  changed", "The event was cancelled", "The client needs fewer staff", "Weather or safety",
  "Another reason", and for one person's booking only (Phase 10, from the dashboard's "Bookings to
  check") "They've left, or can't work here". The words go in the log; free text never does.
- **Cancel a shift** (`cancelShiftByFirm()` in `src/lib/roster/cancel.ts`): each confirmed booking
  is cancelled through the plug (`cancelled_firm`, the reason's words on the row, notice hours from
  the start), logged `shift.cancelled` {by: "firm", shiftId, workerId, reason, noticeHours, strike,
  place: "session_cancelled"}. Then
  the shift is `cancelled`, offers still out expire, and `shift.cancelled_by_firm` {by, reason,
  bookings} is logged. Not a started shift, and not a Google Sheet's.
- **Cancel one booking**: `cancelBooking()` with `by: office` and a reason from the list, whose
  words also go in its event. The worker is told. With "The client needs fewer staff" (Phase 10
  task 19, audit L20) the place goes too: the shift needs one person fewer (`removeFreedPlace()` in
  `src/lib/roster/native.ts`; the highest place still held moves down into the freed one, so the
  places stay 1 to n), logged `shift.changed` {by: "firm", fields: ["headcount"], from, to,
  reason, moved: {assignmentId, fromSlot, toSlot} when the highest place, booked or empty, moved
  down into the freed one}, and nobody is
  offered it, even close to the start; it doesn't restart fair rotation's hold on the shift's other
  open places. The office is told "The shift now needs {n} people." Refused, with nothing changed
  (`keeps_place`), for a shift's last place ("To drop it, cancel the whole shift.") and a Google
  Sheet's shift (its places are set in the sheet). Any other reason reopens the place as before. (How the office records a worker's own
  cancellation when they ring in is parked for Dylan: for now any office cancellation is the
  firm's.)
- **Move or shorten** (`moveShiftByFirm()` in `src/lib/roster/firm-change.ts`): new date, times
  and/or site. It's curtailed when the new times sit inside the old ones at the same site,
  otherwise moved. First the rules are run for each booked worker at the new time: if anyone fails a
  check the office can't override (a credential not in date through the new day, their role, a
  clash; or no answer at all, their record missing), nothing moves (`blocked`, with their names and
  reasons: cancel those bookings first), and the refusal is logged in a short transaction of its
  own: `shift.move_refused` {by, reason, workers: [{workerId, codes}]}.
  Per confirmed worker: `shift.curtailed` / `shift.moved` {by, shiftId, workerId, reason,
  oldStartsAt, oldEndsAt, newStartsAt, newEndsAt, oldSiteId, newSiteId, noticeHours (from the
  earlier of the old and new start, Phase 10: a move earlier records the warning the worker had of
  the new time, so the notice report flags it; the Sheets sync counts the same way), rulesOk,
  codes?}. Each booked worker's row is held (after the shift's, in id order) before the rules run
  for them, so a booking of theirs at that moment finishes first and is seen. Plus
  `shift.changed` for the shift (from/to times and site), and offers
  still out expire. Workers with only overridable problems (rest, hours, a day off) stay booked and
  are listed for the office.
- **Telling each worker**: every one of those events queues `firm-change-notice` (below).

## Errors and observability

- Structured logs (JSON), phone numbers masked, request IDs. `src/lib/log`: one JSON line per
  event; every string is masked (phone numbers in any format, emails), secret and name fields are
  replaced, database error details and drizzle's query parameters are withheld. `src/proxy.ts`
  gives every request a fresh `x-request-id` (client values are overwritten); pages and actions
  log through `requestLog()`. Jobs log `queue`, `jobId` and `firmId`. pg-boss errors keep only
  whitelisted fields and repeat at most once a minute.
- Alerts to the founder: job failure after final retry, webhook signature failures spike,
  sync errors, health check down, Twilio delivery error rate > 5%; since P4.8 a backlog too (jobs
  waiting past their queue's limit or running near theirs, the worker waiting for connections, a
  firm's AI fallbacks, messages or offers far above the usual). Built in Phase 8 short of the
  phone (`ops-alerts-tick` and `ops-alert` above; `src/lib/ops/`): every alert today is an
  `ops alert` error line in the log. Bad webhook signatures are counted in the web process's memory
  (`src/lib/ops/signature-spike.ts`: per-minute counts for the last hour; 20 or more send one
  alert, then at most one an hour; a restart starts again; the webhook doesn't wait for it), since the web can only queue firm jobs
  and a row per bad request would let anyone fill the database. The server being down altogether
  is the outside uptime check's to report (docs/runbooks.md "Monitoring and alerts (once)").
- Weekly digest of job stats.
